> **Réponse courte :** un agent IA WhatsApp multi-sites doit combiner cohérence centrale et adaptation locale. Le siège définit les règles, les sources et les seuils de qualité ; les agences gardent la main sur les demandes qui exigent du contexte terrain.

## Pourquoi le multi-sites est différent

Dans une PME simple, une conversation WhatsApp arrive souvent à une équipe unique. Dans un réseau d'agences, une franchise ou une organisation multi-sites, le même message peut concerner une ville, un point de vente, un commercial, un stock local, un agenda ou une règle interne.

Ce guide complète la page pilier [déployer un agent IA WhatsApp](/fr/blog/deployer-agent-ia-whatsapp-guide-operationnel), l'article [Agent IA WhatsApp CRM](/fr/blog/agent-ia-whatsapp-crm-pipeline-commercial) et la page [secteurs](/fr/secteurs).

## Les quatre niveaux de règles

| Niveau | Exemples | Responsable |
|---|---|---|
| Global | ton, conformité, opt-in, marque | siège |
| Métier | qualification, support, rendez-vous | direction métier |
| Local | horaires, zone, disponibilité | agence ou site |
| Exception | litige, demande sensible, VIP | humain désigné |

Un agent IA multi-sites doit savoir à quel niveau il se trouve. Il ne doit pas inventer une disponibilité locale si l'information n'est pas connectée.

## Routage local

Le routage peut s'appuyer sur plusieurs signaux :

- numéro ou canal d'entrée ;
- ville mentionnée ;
- historique CRM ;
- code postal ;
- agence favorite ;
- produit ou service demandé ;
- langue ;
- disponibilité d'une équipe.

Quand le signal est incertain, l'agent pose une question simple : zone, agence concernée ou préférence de contact. Mieux vaut une clarification courte qu'un transfert erroné.

## CRM central et vues locales

Le CRM doit éviter deux écueils : une donnée trop centralisée que les agences n'utilisent pas, ou une donnée fragmentée que le siège ne peut pas piloter.

La bonne approche consiste à conserver une fiche unifiée, avec des droits et vues par site. L'agent peut enrichir la fiche centrale tout en assignant la prochaine action à l'agence locale.

## Base de connaissances hybride

Une base de connaissances multi-sites doit distinguer :

1. réponses communes ;
2. règles par métier ;
3. informations locales ;
4. cas exclus ;
5. consignes d'escalade.

Si une information locale manque, l'agent doit le dire ou transférer. Il ne doit pas compléter au hasard.

## Qualité par site

Les KPI multi-sites doivent aider, pas sanctionner. On peut suivre :

- délai de reprise ;
- demandes par intention ;
- conversations transférées ;
- fiches CRM complètes ;
- corrections humaines ;
- satisfaction ;
- questions sans réponse.

Le guide [KPI agent IA WhatsApp](/fr/blog/agent-ia-whatsapp-kpi-tableau-bord) explique comment lire ces indicateurs.

## Escalade et responsabilité

Dans un réseau, l'escalade doit être nominative ou au moins rattachée à une équipe claire. Un transfert vers une boîte générique recrée le problème initial : personne ne sait qui doit répondre.

Le guide [escalade humaine WhatsApp IA](/fr/blog/agent-ia-whatsapp-escalade-humaine) propose les règles de reprise à adapter aux organisations multi-sites.

## Questions fréquentes

### Faut-il un agent par agence ?

Pas forcément. Un agent central peut router localement si les règles, droits et sources sont bien structurés.

### Comment gérer les différences locales ?

Avec des blocs de connaissances locaux, des droits par site et une règle claire : l'agent n'utilise que les informations validées.

### Le siège peut-il garder une vue globale ?

Oui. Le CRM et le tableau de bord doivent remonter les intentions, volumes, reprises et corrections par site.
